# Обоснование конфигурации инфраструктуры (Yandex Cloud)

В данном документе описан выбор технических решений, типов ресурсов и параметров конфигурации Terraform для проекта «Будущее 2.0». Архитектура адаптирована под возможности облачного провайдера Yandex Cloud с учетом требований к производительности, безопасности и стоимости.

## 1. Выбор вычислительных ресурсов (Compute Cloud)

Для виртуальных машин была выбрана платформа **Intel Ice Lake (`standard-v3`)**, так как она обеспечивает оптимальное соотношение цена/производительность для большинства серверных нагрузок.

### Airflow Server (Оркестратор)
* **Конфигурация:** 2 vCPU, 4 GB RAM.
* **Гарантированная доля vCPU (`core_fraction = 50`):**
    * *Обоснование:* Компоненты Airflow (Scheduler, Webserver) не создают постоянной 100% нагрузки на процессор. Использование прерываемой производительности (аналог AWS burstable instances, серия T) позволяет снизить стоимость владения (TCO) без ущерба для стабильности.
* **Диск:** `network-hdd` (20 GB). Для хранения логов и кода DAG-ов стандартного сетевого диска достаточно.

### ClickHouse Server (Витрина данных)
* **Конфигурация:** 2 vCPU, 8 GB RAM.
* **Гарантированная доля vCPU (`core_fraction = 100`):**
    * *Обоснование:* СУБД ClickHouse чувствительна к задержкам CPU при выполнении запросов. Использование 100% доли гарантирует стабильное время отклика (latency) и отсутствие троттлинга.
* **Оперативная память:** 8 ГБ — минимально рекомендованный объем для эффективной работы алгоритмов сжатия и агрегации данных в памяти.
* **Дисковая подсистема (`network-ssd`):**
    * *Обоснование:* Для данных ClickHouse выделен отдельный диск типа **SSD** (аналог AWS io2/gp3). Колоночные базы данных генерируют высокую нагрузку по IOPS при слиянии кусков данных (merge tree). Использование медленных HDD стало бы узким местом системы.

## 2. Сетевая архитектура и безопасность (VPC)

Реализована топология с разделением на публичную и приватную зоны (DMZ pattern).

### Публичная подсеть и NAT Gateway
* **Ресурс:** `yandex_vpc_gateway` (Managed NAT).
* **Обоснование:** Использование управляемого шлюза надежнее, чем создание собственной NAT-инстанс (виртуальной машины), так как провайдер гарантирует его доступность. Это позволяет серверам из приватной сети скачивать обновления и пакеты Python (pip), оставаясь невидимыми из интернета.

### Приватная подсеть
* **Изоляция:** Серверы Airflow и ClickHouse размещены в подсети, таблица маршрутизации которой направляет трафик через NAT Gateway.
* **Отсутствие публичных IP (`nat = false`):** Это критическая мера безопасности. Прямое подключение к базам данных и оркестраторам из интернета невозможно, что исключает вектор атак через сканирование портов. Доступ администраторов возможен только через VPN или Bastion Host (промежуточный узел).

## 3. Хранилище данных (Object Storage)

* **S3 Data Lake:** Использование объектного хранилища (аналог AWS S3) вместо файловых серверов обеспечивает:
    1.  **Масштабируемость:** Объем данных не ограничен размером диска VM.
    2.  **Экономичность:** Стоимость хранения "холодных" данных ниже, чем на SSD дисках.
    3.  **Совместимость:** Стандарт S3 поддерживается большинством инструментов Big Data (Spark, Airflow, ClickHouse).

## 4. Декларативный подход

Использование Terraform реализует декларативную парадигму управления инфраструктурой.

* **Суть:** Мы описываем *желаемое конечное состояние* (Desired State) — "хочу 2 сервера и 1 сеть", а не алгоритм их создания.
* **Преимущества перед скриптами (Bash/CLI):**
    * **Управление зависимостями:** Terraform сам понимает, что сначала нужно создать сеть, потом подсеть, и только потом виртуальную машину. В скриптах эту логику пришлось бы прописывать вручную.
    * **Идемпотентность:** Повторный запуск конфигурации безопасен. Если ресурс уже существует и соответствует описанию, Terraform ничего не сделает. Скрипт в таком случае мог бы создать дубликаты или упасть с ошибкой.

## 5. Infrastructure as Code (IaC)

Подход "Инфраструктура как код" обеспечивает:

### Воспроизводимость (Reproducibility)
Весь проект описан в текстовых файлах. Это позволяет поднять **идентичную копию** инфраструктуры (например, для среды тестирования `Stage` или для Disaster Recovery) за несколько минут, просто изменив файл переменных `terraform.tfvars`. Исключается человеческий фактор ("забыл нажать галочку в консоли").

### Масштабируемость (Scalability)
Для изменения масштаба (например, увеличения размера диска ClickHouse с 50 ГБ до 500 ГБ или добавления оперативной памяти) достаточно изменить одно число в коде и применить изменения (`terraform apply`). Terraform автоматически обработает обновление ресурсов, минимизируя время простоя.
