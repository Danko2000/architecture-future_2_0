# Архитектура платформы «Будущее 2.0»: Целевое состояние (To-Be)

## 1. Анализ и приоритизация проблем (As-Is)

В ходе аудита текущего ландшафта выявлены критические архитектурные ограничения. 
Основным барьером является совокупность устаревшего хранилища, монолитной интеграции и унаследованных интерфейсов.

### Таблица проблем и влияния на бизнес

| Проблема | Влияние на бизнес-сценарии | Приоритет (MoSCoW) | Категория (Эйзенхауэр) |
| :--- | :--- | :--- | :--- |
| **Монолитный ESB (Legacy Apache Camel)**. Вся логика, валидация и трансформации "зашиты" в одну трубу. Жесткая связность. | **Блокировка Time-to-Market.** Подключение новых партнеров или сервисов (ИИ, Фарма) требует месяцев доработки ядра интеграции. | **Must Have** | **Важно и Срочно** |
| **Legacy DWH (SQL Server 2008)**. Снят с поддержки, единая точка отказа. | **Риски потери данных.** Невозможность масштабирования под объемы Big Data. | **Must Have** | Важно и Срочно |

## 2. Целевая архитектура (To-Be, 1 год)

Для реализации стратегии выбрана **Гибридная событийно-ориентированная архитектура (Event-Driven Data Mesh)**. Она разделяет владение данными между доменами и вводит потоковую обработку.

### Основные компоненты (Контейнеры C4)

#### 1. Слой Интеграции и Стриминга (Integration Layer)
*Ключевое изменение для поддержки Real-time.*
* **Event Bus (Apache Kafka):** Центральная нервная система. Обеспечивает асинхронную доставку событий между доменами.
* **Integration Logic / FLC (Camel / Kafka Connect):** "Умные коннекторы". Выполняют валидацию (ФЛК) и трансформацию данных *до* их попадания в озеро. Отсеивают "мусор".

#### 2. Платформа Данных (Data Platform)
* **Data Lake (S3):** Хранение сырых данных (Raw), очищенных (Silver) и архивов. Дешевое хранение истории.
* **Витрина Данных (ClickHouse):** OLAP-хранилище для сверхбыстрой аналитики.
* **Orchestrator (Apache Airflow):** Управление сложными Batch-процессами и ночными пересчетами.

#### 3. Доменные Сервисы
* **Legacy Zone:** SQL Server + PowerBuilder остаются как мастер-система для ввода мед. данных. Подключаются к шине через CDC.
* **Fintech & AI:** Микросервисы (Go/Java/Python), работающие с Kafka.

#### 4. BI Portal (Самообслуживание)
* Единая точка входа для аналитиков (Superset/PowerBI). Работает поверх витрин ClickHouse, не нагружая транзакционные системы.

## 3. Обоснование решения и поддержка сценариев

### Сценарий А: Независимое развитие (Decoupling)
* **Проблема:** Изменение в Финтехе требует правок в монолите.
* **Решение:** Внедрение **Kafka**. Финтех-команда подписывается на топики событий и не зависит от релизного цикла Legacy-системы.
* **Результат:** Ускорение вывода продуктов (Time-to-Market).

### Сценарий Б: Скорость и Real-time аналитика
* **Проблема:** Отчеты строятся часами, данные устаревают.
* **Решение:** Комбинация **Kafka + ClickHouse**. "Горячие" данные попадают в отчеты за секунды (Streaming), "холодные" агрегируются ночью (Airflow).
* **Результат:** Дашборды актуальны в любой момент времени.

### Сценарий В: Безопасность и Разделение (Security)
* **Проблема:** Все данные в одной куче, риск утечки диагнозов.
* **Решение:** Физическое разделение на зоны в **Data Lake**.
    * *Raw Zone:* Содержит ПДн, доступ закрыт.
    * *Public/Mart Zone:* Содержит только обезличенные ID и агрегаты.
* **Результат:** Аналитики видят цифры, но не видят диагнозы. Соблюдение закона.

### Сценарий Г: Качество данных (ФЛК)
* **Проблема:** Ошибки в данных ломают отчеты.
* **Решение:** Валидация вынесена на вход (в слой Camel). Некорректные данные не попадают в хранилище, а уходят в очередь ошибок (DLQ).

### Сценарий Д: Масштабирование (M&A)
* **Проблема:** Долгая интеграция купленных компаний.
* **Решение:** Унифицированный протокол. Новые бизнесы просто подключаются к шине данных через стандартные адаптеры, минуя сложную интеграцию "точка-точка".
