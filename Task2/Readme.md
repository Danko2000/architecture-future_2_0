Для реализации архитектурной независимости и отказа от монолитного DWH мы переходим к модели **Data Mesh**. В этой парадигме данные рассматриваются как продукт, за который отвечает конкретная команда (домен), а не центральный отдел DWH.

## 1. Определение доменов

Мы выделяем 4 основных существующих домена и 2 перспективных (для партнеров).

### A. Домен «Клиника и Пациенты» (Core Domain / Legacy Wrapper)
* **Ответственность:** Управление медицинскими картами, расписанием врачей, историей болезней и приемов.
* **Источники:** Legacy DWH (SQL Server 2008), PowerBuilder App.
* **Задача:** Инкапсулировать старый DWH. Вместо того чтобы пускать другие системы "копаться" в таблицах SQL Server, этот домен публикует «чистые» данные в Озеро (Data Lake).
* **Что отдают наружу:** События «Запись создана», «Диагноз поставлен» (обезличенно).

### B. Домен «Финтех» (Strategic Domain)
* **Ответственность:** Кредитование, счета, оплата услуг, страхование.
* **Источники:** Новые микросервисы (Go/Java), PostgreSQL.
* **Задача:** Развиваться быстро, внедрять новые продукты без оглядки на медленную медицинскую систему.
* **Что отдают наружу:** Транзакции, статусы кредитов, финансовые потоки.

### C. Домен «ИИ и Диагностика» (Innovation Domain)
* **Ответственность:** Анализ снимков, второе мнение, предиктивная аналитика.
* **Источники:** Python-сервисы, GPU-кластеры.
* **Потребитель:** Забирает снимки из Озера.
* **Что отдают наружу:** Результаты разметки снимков, вероятность патологий.

### D. Домен «Аналитика 360» (Consumer Domain)
* **Ответственность:** Портал самообслуживания и отчетность для руководства.
* **Источники:** Витрина данных (ClickHouse/BI).
* **Задача:** Собирать данные из всех доменов для кросс-функциональных отчетов.

### E. Перспективные домены (Future Partners)
* **Фармацевтика:** Данные о назначенных лекарствах (интеграция со складом).
* **Электроника (IoT):** Потоковые данные с носимых устройств пациентов.

## 2. Логика потоков данных (DFD)

В новой архитектуре данные перетекают между доменами через центральный хаб (Data Lake), минуя прямые связи "точка-точка". Ниже описан разбор основных потоков.

### Разбор потоков данных

1.  **Поток от Медицины (Legacy):**
    Старый DWH не обрабатывает данные для внешних систем, а только "сбрасывает" их копию (дамп или CDC-лог) в Data Lake (Raw Zone). Это снижает нагрузку на SQL Server 2008.

2.  **Поток от Финтеха:**
    Новые сервисы шлют события о платежах и кредитах параллельно в Озеро. Они не зависят от доступности или структуры SQL Server 2008.

3.  **Сценарий ИИ (Замкнутый цикл):**
    * *Вход:* ИИ-сервис забирает из Озера (Silver Zone) *обезличенные* снимки.
    * *Выход:* После анализа сервис кладет результат (JSON с диагнозом/разметкой) обратно в Озеро.
    * *Ценность:* Врач получает подсказку от ИИ не в момент ввода данных (что могло бы тормозить интерфейс), а асинхронно, либо видит это в аналитическом отчете.

4.  **Сценарий Масштабирования (Партнеры):**
    Фармацевтические компании и производители электроники начинают загружать данные в выделенные папки в Озере (S3). Логика старого DWH при этом не меняется ни на строчку, интеграция происходит на уровне хранилища.

5.  **Сценарий Отчетности:**
    Витрина (например, ClickHouse) собирает данные из всех источников (Финтех + Клиника + ИИ + Фарма) уже внутри Озера, агрегирует их и предоставляет быстрый доступ для BI-портала.

## 3. Аргументация разделения (Преимущества для бизнеса)

Почему выбрана именно такая нарезка доменов и архитектура потоков?

### А. Снижение зависимости от DWH (Decoupling)
* **Проблема:** Ранее добавление поля в отчет требовало изменения схемы в SQL Server 2008, где лежала вся логика.
* **Решение:** В новой схеме SQL Server 2008 — это просто *один из* источников. Если Финтех меняет структуру своих данных, он обновляет свой ETL-скрипт выгрузки в Озеро. Медицинский домен об этом даже не узнает.
* **Бизнес-выгода:** Риск того, что обновление банковского приложения "уронит" работу клиники или заблокирует базу данных, сводится к нулю.

### Б. Ускорение вывода продуктов (Time-to-Market)
* **Сценарий:** Запуск нового продукта "Медицинская рассрочка".
* **Реализация:** Команда Финтеха пишет сервис, сохраняет данные в свой Postgres и настраивает выгрузку в Озеро. Им не нужно ждать, пока администраторы DWH создадут им таблицы или хранимые процедуры.
* **Бизнес-выгода:** Сокращение цикла разработки с месяцев до недель. Команды становятся автономными.

### В. Безопасная интеграция ИИ
* **Сценарий:** Обучение модели на 100 ТБ снимков МРТ.
* **Реализация:** Если бы обучение шло через старый DWH, он бы перестал отвечать на запросы врачей из-за нагрузки. В новой схеме ИИ работает с Data Lake (S3), которое легко выдерживает любую нагрузку на чтение.
* **Бизнес-выгода:** Возможность внедрять тяжелые ML-модели и инновации без деградации производительности основной медицинской системы.

### Г. Готовность к M&A (Слияния и Поглощения)
* **Сценарий:** Покупка Фарма-компании.
* **Реализация:** У купленной компании свои, "чужие" IT-системы. Мы не пытаемся сразу переписать их под наш стандарт. Мы просим их просто выгружать данные к нам в S3 в любом удобном формате.
* **Бизнес-выгода:** Быстрая интеграция управленческой отчетности (за дни), пока идет долгая техническая интеграция (годы).
