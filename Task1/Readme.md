В текущем ландшафте выявлены критические архитектурные долги, блокирующие масштабирование бизнеса. Ниже представлен анализ проблем с привязкой к бизнес-сценариям и приоритизацией (MoSCoW / Матрица Эйзенхауэра).

### Таблица проблем и влияния на бизнес

| Проблема | Влияние на бизнес-сценарии | Приоритет (MoSCoW) | Категория (Эйзенхауэр) |
| :--- | :--- | :--- | :--- |
| **SQL Server 2008 (Legacy DWH)**. Снят с поддержки, не масштабируется, хранит всю логику. | **Риски безопасности и потери данных.** Невозможность обрабатывать сотни ТБ данных от новых направлений (ИИ, Фарма). | **Must Have** | Важно и Срочно |
| **Низкий Time-to-Market отчетов.** Отчеты строятся часами. | **Замедление управленческих решений.** Маркетинг и продажи работают с устаревшими данными. | **Must Have** | Важно и Срочно |

| **Legacy UI (PowerBuilder).** Устаревший интерфейс. | **Операционные неудобства.** Врачам неудобно, но система работает стабильно. | **Could Have** | Не важно, но срочно (операционка) |

## 2. Целевая архитектура (To-Be, 1 год)

Для реализации стратегии выбрана гибридная облачная архитектура с переходом к подходу **Data Mesh**. Это позволит разделить владение данными между доменами (Медицина, Финтех, ИИ) и обеспечить централизованную аналитику.

### Основные компоненты (Контейнеры C4)

1.  **Data Lake (Облачное озеро данных)**
    * *Роль:* Центральное хранилище для всех сырых данных (Raw), очищенных данных (Silver) и архивов.
    * *Технология:* S3-совместимое объектное хранилище.
    * *Обоснование:* Дешевое хранение сотен терабайт, возможность хранить неструктурированные данные (снимки для ИИ, логи оборудования).

2.  **Аналитическая Витрина (Data Mart / Serving Layer)**
    * *Роль:* Обеспечение мгновенного доступа к бизнес-метрикам для BI. Здесь хранятся только *обезличенные* и агрегированные данные.
    * *Технология:* **ClickHouse** (для сверхбыстрой аналитики) или облачный DWH.
    * *Обоснование:* Колоночная архитектура сокращает время построения отчетов с часов до секунд.

3.  **Оркестрация и ETL (Data Integration)**
    * *Роль:* Управление потоками данных между Legacy, Финтехом и Озером.
    * *Технология:* **Apache Airflow**.
    * *Обоснование:* Code-as-infrastructure (Python), гибкость расписаний, легкая масштабируемость воркеров в Docker-контейнерах.

4.  **Доменные сервисы (Источники)**
    * *Legacy Zone:* SQL Server 2008 остается только как источник (Read-Only для аналитики) и OLTP для старых процессов.
    * *Fintech Domain:* Микросервисы на Go/Java со своими БД (PostgreSQL), отдающие события в шину/озеро.
    * *AI Domain:* Сервисы на Python, потребляющие снимки из Data Lake и возвращающие результаты диагностики.

5.  **BI Portal (Самообслуживание)**
    * *Роль:* Единая точка входа для аналитиков. Подключается к Витрине Данных.
    * *Принцип:* Аналитики сами строят отчеты, не нагружая IT-отдел SQL-запросами.

## 3. Обоснование решения и поддержка сценариев

Архитектура спроектирована для решения конкретных болей бизнеса «Будущее 2.0».

### Сценарий А: Быстрая подготовка отчетности
* **Проблема As-Is:** SQL Server захлебывается при агрегации больших объемов, отчеты строятся часами.
* **Решение To-Be:** Внедрение **ClickHouse** в качестве витрины данных. Тяжелые вычисления (JOINs огромных таблиц) переносятся на этап ночной загрузки (ETL в Airflow), а пользователи запрашивают уже подготовленные "широкие витрины".
* **Результат:** Время отклика дашбордов < 1 секунды.

### Сценарий Б: Независимое развитие Финтех и ИИ направлений
* **Проблема As-Is:** Любое изменение в финтех-продукте требует правок в монолитном DWH.
* **Решение To-Be:** Принцип **Data Mesh**. Финтех-команда имеет свою песочницу и свои БД. Они обязаны лишь поставлять данные в Data Lake по контракту (например, JSON/Parquet файлы в S3), не пуская аналитиков внутрь своих транзакционных баз.
* **Результат:** Команды не блокируют друг друга релизами.

### Сценарий В: Масштабирование (покупка Фармы и Электроники)
* **Проблема As-Is:** Добавление новых сущностей требует перестройки схемы БД.
* **Решение To-Be:** Паттерн **ELT (Extract-Load-Transform)**. Данные новых компаний сразу загружаются в Data Lake "как есть". Аналитики могут начать работать с ними немедленно через инструменты Big Data (Spark/Trino), не дожидаясь создания красивых витрин.
* **Результат:** Ускорение интеграции M&A сделок.

### Сценарий Г: Безопасность и регуляторика
* **Проблема As-Is:** Все данные в одной куче.
* **Решение To-Be:** Физическое разделение.
    1.  **Raw Zone (Legacy + S3):** Содержит ФИО и диагнозы. Доступ закрыт для большинства, открыт только для ETL-процессов и спец. сервисов.
    2.  **Public Zone (Витрина):** Содержит только ID клиентов и агрегаты. Финтех-аналитик видит "Клиент 123 потратил 5000 руб", но не видит диагноз.
* **Результат:** Соблюдение врачебной тайны и GDPR/ФЗ-152.
